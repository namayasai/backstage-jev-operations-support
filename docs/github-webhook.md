# GitHub pull request webhook

The backend can synchronously evaluate changed Markdown documents from selected GitHub pull requests with the readiness workflow. The endpoint is disabled unless both the webhook HMAC secret and GitHub API token are configured, and it also requires an explicit repository allowlist and Markdown path filter.

```yaml
jevOperationsSupport:
  apiKey: ${TYPESAFE_API_KEY}
  githubWebhook:
    secret: ${JEV_GITHUB_WEBHOOK_SECRET}
    token: ${JEV_GITHUB_READ_TOKEN}
    repositories:
      - acme/payments
    documentationPaths:
      - docs/**/*.md
      - runbooks/*.md
    # Forks are refused unless this is explicitly true.
    allowForks: false
```

Configure GitHub to send `pull_request` events to `/api/jev-operations-support/webhooks/github` with the same secret. Only `opened`, `reopened`, `synchronize`, and `ready_for_review` actions are evaluated. The handler verifies `X-Hub-Signature-256` over the raw request bytes before parsing JSON. It does not use Backstage user authentication for this route; the configured signature is the authentication boundary. The existing `/evaluate` endpoint continues to require a signed-in user and the Jev permission.

The handler accepts only an exact, case-insensitive repository allowlist entry. `documentationPaths` uses simple glob patterns: `*` matches characters within one path segment, `**` matches nested path segments, and `?` matches one character. Only `.md`, `.mdx`, and `.markdown` files matching one of these patterns are read. A missing filter never means “all files.” Fork heads are refused by default. If forks are explicitly enabled, the contents are read from the event's head repository at the pinned head SHA.

For an accepted delivery, the backend reads the pull request metadata, checks that the event head and base SHAs still match, lists changed files through the paginated GitHub pull request files API, and reads matching contents from the GitHub contents API at that head SHA. It checks the pull request head and base again before evaluation. Payload URLs are never fetched. Each matching Markdown file is evaluated separately with the existing `buildEvaluation` and `summarize` functions using the `readiness` workflow, and the response contains a result for each path. `change-risk` is not inferred from a pull request and no change is marked safe.

**This is true regardless of the `report` setting below.** Reporting only changes *where* the already-computed result is written; it never widens what is read from GitHub or what is sent to Jev. No diff, patch, or PR body is ever read or sent, with or without reporting enabled — **unless the separate, opt-in "Change review" feature described near the end of this document is also enabled**, which does read and send diff/description content, under its own path allowlist.

The default limits are deliberately small: 3 matching documents, 300 changed files, 3 GitHub file-list pages of 100 files (up to 10 pages of 30 when change review runs), 128 KiB per document, and 16,000 decoded bytes across one readiness context. The end-to-end deadline is 1000–8000 ms with `report: none` (see below for the higher bound once reporting is on), and one webhook evaluation runs at a time. The deadline and matching-document count can be adjusted in backend config; the other workload limits are fixed in this integration.

Every matching document is validated against the shared evaluation limits before the first provider call, so a limit violation never happens after an earlier document was already evaluated. A document that is oversized, empty, or too short for a readiness evaluation refuses the whole delivery (`422` with `report: none`, or a written `error` status with reporting on) and names that path only in the `report: none` response body, without calling Jev at all. A provider failure can still occur after an earlier document succeeded; with `report: none` the response is then `503` with `partial: true` and the results obtained so far.

## Reporting the result back to GitHub

By default (`report: none`) the result only ever appears in the HTTP response to this webhook, exactly as described above — nothing is written to GitHub. This is opt-in and strictly additive:

```yaml
jevOperationsSupport:
  githubWebhook:
    # ...same config as above...
    report: status         # none (default) | status | status+comment
    blockOn: never          # never (default) | attention
```

- **`status`** writes a commit status on the pull request's head SHA (`POST /repos/{owner}/{repo}/statuses/{sha}`), with the fixed context `jev/readiness`. **The invariant this integration maintains: every `pending` it writes gets exactly one final state, and nothing at all is written for a delivery that never confirmed a matching document.** `pending` is written the moment at least one changed file is confirmed to match `documentationPaths` — before that file's content is even read — and from that point on the delivery always ends in exactly one of:
  - `success`, even when findings need attention or review (advisory by default, matching the workbench UI), unless `blockOn: attention` and at least one finding has status `attention`, in which case `failure`. A low-confidence `review` finding never blocks by itself.
  - `error` — the evaluation could not be performed (a GitHub read failure *after* the matching document was confirmed, a Jev failure, the per-delivery deadline, or a matching-document-count limit exceeded). The description names the category only, never a document path or content.
  - A **neutral `success`**, with a description containing `Not evaluated — the pull request changed during the check`, written when the pull request's head or base moved after `pending` was written but before evaluation could finish. This resolves the `pending` instead of leaving it dangling forever, without claiming a readiness judgment that was never actually completed. Unlike the two states above, writing this does **not** re-check the head SHA first: reaching it already means evaluation itself detected the move, so a further recheck would only add a read that changes nothing about what gets written.

  A GitHub read failure *before* any matching document is confirmed (for example, the changed-file listing itself hitting the `maxChangedFiles`/page limit) writes nothing at all — there is no `pending` to resolve, and nothing was ever owed. The delivery id is not remembered in that case, so a **manual** GitHub redelivery can retry it after a configuration fix (see "Background processing" below for why this is always manual once reporting is on). Every description starts with the pull request number, e.g. `PR #12 · 2 clear · 1 attention · 1 needs review — advisory`, kept to GitHub's 140-character limit. `target_url` is set only when `app.baseUrl` is configured.

  **`pending` and `error` are ordinary commit statuses, and GitHub branch protection can require this context before a merge regardless of `blockOn`.** `blockOn: never` (the default) means *findings* never fail the status — it does not mean this context can never block a merge: a `pending` sitting on a check still in the (bounded) queue, or an `error` when the check itself could not be completed, are equally "not `success`" to GitHub, and a required status check treats them the same way it treats any other non-passing check. **Do not mark `jev/readiness` as a required status check in branch protection unless that is the intended behaviour.**

  **Known limitation: a commit status is keyed only by (repository, SHA, context), never by pull request.** Two open pull requests that happen to share a commit — a stacked branch, or one rebased onto another's tip — silently overwrite each other's `jev/readiness` status; a genuine `failure` written for one PR under `blockOn: attention` can be replaced by a `success`, an `error`, or the neutral resolution written for the other, with no reconciliation between them. This integration makes the collision visible (every description names its own PR number, as above) rather than preventing it — preventing it would require an extra GitHub read this integration deliberately does not make.

- **`status+comment`** additionally creates or updates exactly one pull request comment, located by a hidden HTML marker that must be the very first thing in the comment body (not merely present somewhere inside it — a comment that quotes the marker without being this integration's own report is never mistaken for it), among the PR's own issue comments authored by the configured token's user. The issue-comments endpoint has no `sort`/`direction` parameters of its own (unlike some other GitHub list endpoints) and is always oldest-first, so finding a *recent* marker within a bounded read is done by reading pages from the end backwards: one request learns the total page count from the response's `Link: rel="last"` header, then up to 3 pages (300 comments) are read starting from the last page and working backwards, each page's own comments checked newest-to-oldest. A marker older than that trailing window is treated as absent, and a new comment is created instead of the old one being updated — a small, accepted limitation of the fixed page bound rather than an unbounded read. **If the commit status write itself could not be posted to GitHub at all, the comment is skipped entirely** — the status is the authoritative signal, and a result table sitting next to a `pending` that never resolved would be actively misleading. The comment otherwise lists, per changed document: the check, the answer in words (the same wording the workbench UI uses, via the shared `formatFindingValue` in `@namayasai/backstage-plugin-jev-operations-support-common`), the status, and the next step, followed by the model, the evaluation time, and the same "a negative finding does not prove the condition is absent" disclaimer shown in the workbench UI.

  **It never includes document content.** Every changed-file path is rendered as an inert Markdown inline code span (backtick-fenced with the fence sized wider than any run of backticks already in the path; C0 control characters and DEL stripped; Unicode bidi-override, zero-width, and other hidden/format characters — which could otherwise make a path display in a misleading order, or hide extra content invisibly, without changing its bytes — stripped as well; and any `|` replaced with a look-alike character), so a hostile path — a Markdown link, an `<img>` tag, an `@mention`, a pipe, an embedded backtick, a right-to-left override — can never become a link, image, HTML element, notification, visually reordered string, or broken table, and is instead rendered as inert literal text. The (always-fixed, never PR-controlled) check title and guidance text are additionally Markdown-escaped and mention-neutralized as defense in depth. The provider's reported model name is treated the same way (code-spanned, capped to 80 characters, same hidden-character stripping) since it is not fully trusted input either. The whole comment body is capped at 60,000 characters; a pull request with an unusually large number of matching documents and findings gets a truncated table with an explicit final row instead of an unbounded comment.

- **GitHub Check Runs cannot be written with this integration.** The Checks API requires a GitHub App installation token; a personal access token cannot create or update Check Runs. This is why reporting uses commit statuses instead, which any token with the right scope can write.
- **Token permissions:** the existing read scopes are always required. `status` additionally needs **Commit statuses: write** (classic PAT: `repo:status`; fine-grained: "Commit statuses" write). `status+comment` additionally needs **Issues: write** (fine-grained — the pull request comment endpoints used here, `GET/POST /issues/{number}/comments` and `PATCH /issues/comments/{id}`, are part of the Issues API rather than a separate "Pull requests" permission; classic PAT: `public_repo`/`repo`) plus **Pull requests: read** (fine-grained) to look up the pull request itself.
- Before writing the real result (`success`/`failure`) or an `error`, the pull request's head is re-checked once more against a fresh read. Only a **confirmed** moved head (a successful read showing a different SHA) suppresses that write and substitutes the neutral resolution above instead; if the recheck read itself fails (a transient GitHub error, a rate limit), the real result or `error` is written anyway — an unconfirmed recheck failure is no riskier than the `pending` already sitting on that SHA, and is not treated as proof the head moved. The neutral resolution's own write, as noted above, skips this recheck entirely.
- The final status write retries a transient failure — a network error, an HTTP `5xx`, or GitHub's `403`/`429` rate limiting — up to twice more with a short backoff (0.5 s, then 1.5 s), inside its own 10-second budget; it does not retry `401`, `404`, or `422`, which will not succeed on a retry. The pre-write head recheck has its own separate 3-second budget so a slow read there cannot itself eat into the write's retry budget, and the comment write (when attempted) has a further separate 5-second best-effort budget with no retries.
- A delivery's dedupe bookkeeping reflects whether a final write actually succeeded: a delivery whose final state (real result or neutral resolution) was successfully posted to GitHub is remembered, so a later GitHub redelivery of the same id is recognized as a duplicate (see "Delivery deduplication" below for the exact responses). If the final write itself could not be posted after every retry above was exhausted, the delivery id is *not* remembered, so a **manual** redelivery retries it — writing a status is treated exactly like evaluating one, for this purpose.
- All GitHub writes use the same fixed `api.github.com` origin as reads, with redirects rejected the same way. A write failure is logged without secrets, request bodies, or document content, and never throws past the background queue below.
- Reporting does not add document content to the Jev request. It does add GitHub head checks and, in comment mode, identity and comment-list reads; see "Reads per delivery" below.

### Background processing

With reporting on, the webhook no longer blocks the HTTP response on GitHub's or Jev's latency: it verifies the signature, dedupe, and allowlist exactly as before, refuses a fork whose webhook payload already makes that obvious (before it ever occupies a queue slot — the authoritative fork check, which needs a GitHub read, still happens once the job is dequeued), then responds `202 Accepted` with `{ accepted: true, deliveryId }` and evaluates in an in-process background queue.

**With reporting on, this webhook always answers `202` for an accepted delivery (or the `503`/`400`/`401` cases described elsewhere in this document) — never the `5xx` that the synchronous `report: none` path can return while evaluation itself is failing.** [GitHub does not automatically redeliver failed webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries). A `202` only confirms acceptance into this local queue, not that evaluation or reporting succeeded. Concretely: if the final write is retried and still fails (see above), the `pending` it was meant to resolve simply stays on GitHub with no further attempt coming — recovery is either a new commit (which starts its own `pending`/final cycle on the new head) or a person clicking **Redeliver** on that delivery from GitHub's own webhook delivery UI.

- The queue runs at concurrency 1 (one delivery evaluated at a time) and has a bounded length (`queueLength`, default 20). A new delivery is refused with `503` and `Retry-After` when the queue is full **or** when the shared delivery-dedupe map itself is at its own capacity (`dedupeMaxEntries`, the same guard the synchronous path already has). A queue-full or dedupe-capacity rejection **is not remembered** — a manual GitHub redelivery is the retry mechanism, and remembering it would make a legitimate redelivery bounce off the dedupe map instead of retrying.
- A newer delivery for the same pull request **supersedes** an older delivery for that same pull request that is still waiting in the queue (never one already being processed). A fresh queued delivery has never reached `pending`, so a later redelivery of it is a duplicate. A queued retry of a partially completed delivery keeps its earlier progress and outstanding final-status obligation; redelivering it again retries only its unfinished context.
- The per-delivery deadline (`timeoutMs`) can be configured up to 60,000 ms in this mode — it no longer holds GitHub's own webhook connection open, so it can afford to wait longer for Jev and for GitHub reads than the synchronous `report: none` path (capped at 8000 ms) can. A deadline exceeded after `pending` was written resolves it with `error`, per the invariant above.
- **The queue is in-process memory only, exactly like the existing delivery dedupe map.** A backend restart loses any queued-but-not-yet-started work with no record of it, and can also leave a `pending` status sitting on GitHub with no in-process worker left to resolve it — the same new-commit-or-manual-Redeliver recovery described above applies. After a restart, the dedupe map is also empty, so manual redelivery can run immediately. While the process is still running, queued/in-flight IDs return `503`; completed IDs return `200` duplicate; partially completed IDs retry their unfinished work. There is no persistent queue, database, or scheduler.
- The authenticated `GET /status` route (which also reports the demo/live evaluation mode) additionally reports, when the webhook is configured: the current `report` mode, the current queue length (`queueLength`), active delivery count (`inFlight`), and the outcome code and time of the last delivery to finish. No repository names, pull request numbers, or document content are ever included.

## Delivery deduplication (both modes)

Delivery IDs are deduplicated in process memory with a bounded map and a ten-minute default TTL. Two distinct responses can come back for a delivery id that has already been seen, depending on where the earlier attempt got to:

- **`503` "already being processed"** (with `Retry-After`): the earlier delivery with this id is still actively running (`report: none`) or is queued/in-flight (reporting on). Retrying immediately will very likely hit this again; wait.
- **`200 { status: 'duplicate' }`**: the earlier delivery with this id already reached a deterministic, non-retryable end state — evaluated successfully, intentionally ignored (repository/fork policy, no matching document), superseded by a newer delivery for the same pull request, or (reporting on) its final report was itself successfully written to GitHub. This is a no-op: nothing is re-evaluated and nothing is written again.

A delivery that instead *failed* outright — a thrown evaluation error, or (reporting on) a final report write that could not be posted to GitHub after every retry — is not remembered at all, so the same delivery id reprocesses from scratch on a **manual** redelivery, rather than returning either response above. The dedupe map is lost when the backend restarts, and there is no persistent queue or scheduler beyond the in-memory one described above. GitHub API, Jev, and deadline failures return `503` (or a sanitized provider status) with `retry: manual` in the `report: none` response body; with reporting on, the same failure categories are instead reflected in the `error` commit status described above.

Logs and HTTP errors do not include webhook secrets, GitHub tokens, request bodies, or Markdown contents. The GitHub token needs read access to the configured repositories (plus the write scopes above when reporting is enabled) and is used only for the fixed `api.github.com` origin.

## Change review (opt-in, requires reporting)

A second, independent integration on the same webhook: for the same accepted deliveries, it assembles a bounded summary of the pull request itself — title, description, changed-file list, and diff excerpts for allow-listed, non-sensitive paths only — and runs the existing `change-risk` workflow (compatibility, data migration, access control, rollback) against it, exactly like a manual "change review" check in the workbench. It is off by default, requires the same repository allowlist and `secret`/`token` as the rest of this webhook, and an explicit path allowlist of its own:

```yaml
jevOperationsSupport:
  githubWebhook:
    # ...secret, token, repositories, documentationPaths, report: status (or status+comment)...
    changeReview:
      enabled: true
      paths:
        - src/**
        - cmd/**
      # maxFiles: 20        # 1-50, default 20 — files that get an actual diff excerpt
      # maxPatchBytes: 12000 # 1000-16000, default 12000 — total UTF-8 byte budget for those excerpts
```

`changeReview.enabled: true` with `report: none` is a **startup error**: the change-review result would never be written anywhere (it has no `report: none` mode of its own — there is nothing to leave only in an HTTP response, since it always runs from the background queue), so the backend refuses to start rather than silently spend a provider call for nothing. This is unrelated to whether readiness itself finds a matching document: change review has no "nothing matched" outcome of its own — once enabled and the pull request's head is confirmed current, it always attempts an evaluation, even for a pull request with no documentation changes at all, and even if every changed file ends up withheld (the assembled text then says explicitly, "No diff excerpts were included.").

**The `changeReview` block is validated strictly at startup, even when `enabled` is left at its default `false`.** A malformed value, an out-of-range `maxFiles`/`maxPatchBytes`, or an unknown key inside `changeReview` all fail the backend at startup — deliberately, since this is a security-relevant, opt-in-to-send-diffs block, an operator who mistypes a key here should find out immediately, not silently have the typo ignored while the (unintentionally still-disabled, or worse partially-misconfigured) feature waits to surprise them later.

### Exactly what is sent to the provider, and what never is

The content-assembly and privacy rules are entirely implemented and documented in `plugins/jev-operations-support-backend/src/changeReview.ts`'s own extensive module doc comment; this section summarizes the parts that matter for an operator, verified against that source:

For an allow-listed, non-fork (or explicitly allowed fork) pull request, the assembled text contains, in order: a fixed preamble; the pull request **title**, forwarded exactly as written and never shortened; the **description**, forwarded exactly as written up to a 4000-character budget; the **changed-file list** (every file's name and stats, with no exception — including sensitive, unsupported-path, and out-of-allowlist files, since this list carries names and stats only, never diff content); and **diff excerpts**, one per file that (a) matches the `changeReview.paths` allowlist on both its current name and, for a rename, its previous name, (b) is not flagged by the sensitive-path heuristic on either name, and (c) has a patch with actual (non-whitespace, non-zero-width) content. A removed file is not special-cased: an allow-listed, non-sensitive deletion is sent as an ordinary diff excerpt like any other change.

**Bold, because it is easy to miss: the title and description are sent to the provider exactly as written, with no sensitivity filtering.** Neither the path allowlist nor the sensitive-path heuristic ever look at title or description content — they only ever decide whether to withhold a *diff excerpt*. A secret pasted into a PR title or description is sent.

Two different things withhold a file's patch, reported under two different fields so neither overstates what was actually established: `excludedSensitive` is a genuine match against a denylist of secret/credential-shaped path segments (`.env` and its variants, `*.pem`, `*.key`, `id_rsa*`, `*secret*`, `.npmrc`, `.kube/config`, and more — see the source for the full list); `unsupportedPath` means the path heuristic could not confidently evaluate the name at all (a literal backslash, a disallowed non-ASCII punctuation/symbol character outside a small allowlist of everyday Japanese punctuation, or an over-long name) — it was never actually matched against anything, and is not itself evidence of anything sensitive. **This is a path heuristic, not secret scanning:** a file that does not match is not thereby known to be safe, and a file that does match is excluded even if it holds nothing sensitive. A rename is only as safe as its less-safe name — a name that was ever sensitive, unsupported, or outside the allowlist withholds the diff regardless of what the file is called now.

Diff content beyond `maxPatchBytes`, diff content for a file outside `changeReview.paths` or flagged by the sensitivity heuristic, diff content for a binary file or one with no real patch content, a raw bidi override/isolate control character (replaced by a visible `<U+XXXX>` placeholder wherever displayed), and any pull-request metadata beyond title/description/changed-files/diffs (comments, reviews, approvals, payload URLs) are never sent, under any configuration. GitHub's file-listing pagination/count limits (shared with readiness's own `maxChangedFiles`/`maxPages`) apply here too, but — unlike readiness, which refuses the whole delivery over the limit — a change-review listing that hits them is **truncated, not refused**: a huge pull request still gets a change review of whatever was listed, with the truncation disclosed (`filesTruncated`) rather than silently dropped. So is a single listing *page* that itself exceeds GitHub's 1 MiB response cap once real diff text is included, EXCEPT when it is the very first page: nothing at all could be collected yet in that case, so it is a genuine error recorded in `/status` for both contexts. A fresh delivery has not confirmed a match or written pending yet, so it writes no commit status; a partial retry resolves any earlier pending with an error. To keep an ordinary-sized pull request's listing pages well under that 1 MiB cap even with real patch text included, change review pages the listing at 30 files/request and scales the page budget to 10, preserving the 300-file cap. Readiness alone keeps 100 files/request and 3 pages. An explicit final-page Link header allows exactly 300 files to complete; if another page exists, readiness refuses the incomplete listing and change review discloses truncation.

If even the title alone cannot fit the shared 16,000-character / 24,000-byte evaluation budget (every other section already removed), change review is not run for that pull request: `jev/change-review` gets a fixed, content-free `error` status ("The pull request summary could not be assembled within limits."), and the provider is never called.

### Reads per delivery, and how the two contexts share them

Readiness and change review, when both apply to the same delivery, share a **single** pull-request read and a **single** changed-file listing read up front, rather than each reading GitHub independently:

1. **One `GET .../pulls/{n}`** for the pull request itself (SHA/base staleness, and — only when change review is enabled — its `title`/`body`).
2. **One changed-file listing** (`GET .../pulls/{n}/files`, however many pages that takes) — with `patch`/`additions`/`deletions`/`previous_filename` parsed and kept **only when `changeReview.enabled`**; readiness's own read, when change review is disabled, retains none of those fields, matching its behaviour from before change review existed.
3. **One shared "before evaluating" staleness recheck** (`GET .../pulls/{n}` again), immediately before either context's own evaluation work starts, for whichever context(s) are about to run.
4. Readiness's own document reads (`GET .../contents/{path}`), one per matching Markdown file — unrelated to change review, which never reads a file's content (only the listing's own `patch` field).
5. Each context's own **final-write staleness recheck**, immediately before its own status write (`reportFinal`/`reportChangeReviewFinal`'s existing `checkHead`) — one read each, independent of the other context.

Concretely, for a delivery with N matching readiness documents: **readiness alone is 3 + N pull-request-equivalent reads** (steps 1, 3, 5, plus N document reads) **plus the listing**; **with change review also enabled, it is 4 + N** (steps 1, 3, 5 for readiness, 5 for change review, plus N document reads) **plus the (now change-review-sized) listing** — one extra read total, not one extra per context, because steps 1 and 3 are shared.

The counts above cover evaluation and status reporting without retries. In `status+comment` mode, writing the shared comment also reads `GET /user` once per client lifetime (cached after success) and the issue-comment listing. The listing reads page 1 to discover the last page, then up to `maxCommentPages` recent pages: at most `maxCommentPages + 1` HTTP reads, fewer when page 1 is inside that window. GitHub write retries can repeat their own head checks. Comment/status writes themselves are additional requests.

### The job deadline is split between evaluations

When both contexts need evaluation, readiness's evaluation deadline is shortened by `min(15 s, timeoutMs / 2)`; change review uses the full deadline measured from job start. With the default `timeoutMs: 8000`, readiness therefore has only 4000 ms from job start. For reporting with both contexts, start with `timeoutMs: 30000` and increase up to 60000 as needed for the provider and GitHub latency. The shared preparation reads and separately bounded final-status writes can consume the intended reserve, so it is not a guaranteed minimum execution time for change review. A timed-out context resolves its pending status with an error. When change review is disabled or already completed on a retry, readiness keeps the full deadline.

### Redelivery resolves only the context that did not finish

A delivery whose two contexts (readiness, and — only when `changeReview.enabled` — change review) did not BOTH reach a successfully-written final state is remembered as `partial`, not simply forgotten: it records which context(s) already finished. A later GitHub redelivery of the *same* delivery id then re-queues (rather than bouncing as a `503` "already being processed" or a `200` duplicate) and **skips whichever context is already done** — no second provider call for it, no `pending` flip on its already-final status — running only the one that is not. A delivery whose contexts BOTH finished is still an ordinary `200` duplicate, as always; a delivery where neither context finished and no pending write was attempted is forgotten. If pending was attempted, that obligation is retained even if both final writes failed. If the PR head moves before a retry, only the unfinished contexts are resolved neutrally on the original SHA; completed contexts are untouched. This `partial` state, and the per-context skip it enables, only ever exists when `changeReview.enabled` — with change review off, redelivery behaves exactly as it always has (a delivery is either fully done or forgotten, nothing in between).

### Status: `jev/change-review`

A second, independent commit status context, alongside `jev/readiness` — same `PR #N · ...` prefix, same 140-character cap, following the same pending → exactly-one-final-state invariant, but never affecting or affected by the readiness result. Its description is derived honestly from the four `change-risk` checks (`breaking`/`migration`/`access` are *concern* checks — `summarize` never reports them as `pass`: a low probability there is "not established", still `review`, never evidence the change is safe; only a high probability reports `attention`. `rollback` is the inverse of a concern — `pass` there means rollback IS documented):

```
PR #12 · 1 concern · 2 not established · rollback documented — advisory
```

`blockOn: attention` (the same setting readiness uses) fails `jev/change-review` only when at least one CONCERN finding is `attention`; a `review` finding — including an unestablished concern or an unclear/undocumented rollback — never blocks by itself.

### Comment: one shared marker, a new section

In `status+comment` mode, the change-review result is appended as a "Change review" section to the *same* hidden-marker comment readiness already writes (never a second comment): its own findings table (same renderer, same `formatFindingValue` wording as readiness), the standing disclaimers, then a collapsed `<details>` disclosure block summarizing what was included, listed only, excluded as sensitive, withheld as an unsupported path, or had no diff available, with counts in the summary line. Every disclosed path renders through the same inert `codeSpan` renderer readiness already uses (Markdown/HTML-inert, hidden-Unicode-stripped) and every reason through the same plain Markdown escaper; only `path`/`reason` are ever rendered, never the raw, un-display-safe path a wiring layer might otherwise have access to. The standing disclaimers are: the same negative-finding disclaimer readiness's own footer carries, "'Not established' is not evidence that the change is safe," and "Sensitive paths are withheld by a path heuristic, not secret scanning; the pull request title and description are sent as written." **The diff content and the PR description are never included in the comment — only path names, reasons, counts, and the four findings.**

**Budgeting order (so a large readiness table can never silently push the change-review section, its disclaimers, or its `<details>` block off the end):** the change-review section is built and its length reserved FIRST, normally at its full size (every disclosure category listing up to 50 entries); only if it would not fit the comment's own 60,000-character cap on its own does it degrade, by shrinking the per-category entry cap (50 → 25 → 10 → 5 → 1 → 0, with an "... and N more" tail) — the findings table, the standing disclaimers, and the `<summary>` line's own counts are never dropped by this degradation, only the itemized per-category path lists are. Readiness's table then gets whatever budget remains, absorbing any shortfall through its own existing row-level truncation (with its own visible truncation row) exactly as it always has. The whole comment stays under the 60,000-character cap either way, as a last-resort hard clip that should not be reachable in ordinary use now that both sections reserve their own budgets up front.

### Error wording is context-specific

`jev/change-review`'s `error` status never reuses `jev/readiness`'s own wording — a reader seeing "A changed document exceeded a configured evaluation limit." under `jev/change-review` would reasonably (and wrongly) think a document was involved, when change review never reads one:

| Failure | `jev/readiness` says | `jev/change-review` says |
| --- | --- | --- |
| Per-delivery deadline exceeded | "Jev readiness check exceeded its processing deadline." | "Change review exceeded its processing deadline." |
| A GitHub limit was hit (listing/page/size) | "A changed document exceeded a configured evaluation limit." | "The pull request could not be listed within limits." |
| GitHub could not be read | "GitHub could not be read for this pull request." | "GitHub could not be read for change review." |
| Jev (the provider) failed | "Jev evaluation failed." | "Change review could not be completed." |
| The assembled text could not fit the evaluation budget | *(not applicable to readiness)* | "The pull request summary could not be assembled within limits." |
| Anything else unrecognized | "Jev readiness check could not be completed." | "Change review could not be completed." |

A failure in the SHARED steps (the pull request read, the listing, or the shared pre-evaluate recheck — see "Reads per delivery" above) is reported to BOTH contexts that were about to run, each in its own wording from the table above.

### Cost, tokens, and privacy

One extra provider call per accepted delivery when `changeReview.enabled` (the readiness path's own document-count limit, `maxDocuments`, is unaffected — the total provider calls per delivery stays at `maxDocuments + 1` at most). No new GitHub API endpoint: change review reads only the same pull-request-files listing and pull request metadata described in "Reads per delivery" above — no raw diff download, no payload URL fetch. Token permissions for change review are identical to reporting's own: no separate scope. **Privacy: with `changeReview.enabled: true`, diff content for allow-listed, non-sensitive paths leaves this host and is sent to the configured Jev/TypeSafe endpoint**, in addition to whatever readiness already sends — operators who need to keep a subtree's diffs entirely off that endpoint should exclude it from `changeReview.paths` rather than relying on the sensitive-path heuristic, which is a best-effort filter, not a guarantee.
