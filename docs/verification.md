# Verification

## Version 0.4.0 release verification

All five packages are public on npm at 0.4.0 with the `latest` tag. Anonymous downloads matched both registry SHA-512 integrity and the reviewed archives byte for byte. A fresh consumer installed all five by registry name with an empty user configuration and verified package entry points, backend CJS/ESM imports, the response-planner export and the AWS migration directory. See [0.4.0 publication verification](npm-publication-0.4.0.json).

The 0.4.0 release includes the dedicated Alerts, Triage and Pre-check pages, PR reporting, entity cards and optional OpenAI, Claude and compatible-API response planning. Release checks passed 865 tests across 26 files on Node.js 22, type checking, all five package builds, and the fixture demo build. All five 0.4.0 archives were then installed together into a clean npm consumer. Backend/common/module CJS and ESM imports, frontend entry-point resolution, the response-planner demo, and the packaged AWS migration directory passed. Archive contents and internal dependency versions were checked before publication. Earlier 0.2.0 and 0.3.0 results below are historical records, not a claim of live-LLM validation for 0.4.0.

The latest real Backstage host checks used packed artifacts with synthetic/demo data: navigation, alert selection, receipt and manual results, LLM suggestion display, pre-check tabs, both frontend systems' entity cards, search ordering and the template creation route. Provider protocol/error tests use mocks; no live OpenAI, Claude, or compatible-API quality evaluation is claimed.


The automated suite covers workflow contracts, malformed and contradictory provider responses, uncertainty handling, no-match decisions, risk polarity, result ordering, identity and permission checks, rate limits, provider failures, browser component interactions, catalog API adaptation, and entity navigation state.

`npm run check` runs type checking, all tests with two workers, the five package builds, the fixture demo build, and an isolated archive-consumer check. `npm run test:packages` runs the archive check alone after building: it packs all five workspaces, checks versions, published file paths and archive integrity, installs the archives outside the repository with an empty npm configuration and install scripts disabled, and checks runtime imports, every export target, demo evaluation and packaged migration entry points. This consumer requires public registry access for dependencies; it does not require Jev, LLM or npm publishing credentials. It uses `--legacy-peer-deps` to isolate packaging validation from Backstage host peer resolution; frontend exports are resolved, not rendered. It does not replace testing the supported host configuration.

The workflow in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs the same command for pull requests and pushes to `main`, with read-only repository permissions and no persisted checkout credentials. It can also be started manually. CI checks are distinct from branch protection: a maintainer must require the `Check and package validation` status in repository rules to prevent merges without it. Release preparation should run `npm run check` before publishing the reviewed archives.

The post-0.4.0 CI/retention changes passed `npm run check` locally on Node.js 22.14.0: 869 tests in 26 files, type checking, all five package builds, the fixture demo build, and installation/import checks for all five archives. No live provider or AWS calls were used for this validation. Node.js 26 with the current jsdom version fails browser tests during localStorage setup; Node.js 22 is the CI baseline.

The optional modules import the backend's `/client` export, and the frontend and backend import the common package. Type checking and the Vitest run resolve both through narrow source aliases in `tsconfig.json` and `vitest.config.ts`, so they do not depend on a previously built `dist`. The root `build` script lists its workspaces explicitly so `common` and `backend` are built before their consumers; there is no build orchestrator. `npm run check` was verified from a state with all five generated `plugins/*/dist` directories moved aside, not only from warm caches.

The live smoke harness makes eight calls with synthetic English input: one per workflow, plus complete readiness documentation and a template no-match case. The last two cases assert an expected decision; the first six validate the response contract and record the output. Timing includes the client-to-provider round trip in one local run. It is a schema/connectivity smoke test, not an accuracy benchmark.

The opt-in `npm run eval:live -- --key-file /absolute/path/to/raw-key --repeat 3` harness reads [evaluation-fixtures.json](evaluation-fixtures.json). It covers Japanese, Japanese/English mixed text, negation, implicit evidence, and insufficient context with explicit expected labels. The report records each check's observed status, expected status, value, confidence, label match, and aggregate review rate. Repetition is optional and is useful for observing model variation; the small fixture set does not establish production precision or recall. The key is read into memory only and is never written to the report.

One run on 2026-09-19 with 15 calls and 60 checks matched 57 expected labels and produced a 35% review rate. The three mismatches were the same implicit rollback fixture on each repeat: the expected `attention` label was returned as `review`. The result is a documented limit of this small fixture and model behavior, not an accuracy claim; the evaluation command reports the mismatch and exits nonzero while retaining the report.

The report in [live-smoke.json](live-smoke.json) includes the actual model ID, selected values, probabilities where available, confidence, and timestamps. Credentials and provider error bodies are excluded.

Browser verification exercised all six fixture workflows using the shared React workbench. Current screenshots show the [real Backstage host](backstage-workbench.png) and a [live Jev result](backstage-result.png).

## Optional module coverage

The automated suite passes 120 tests across 11 files. The 0.3.0 packages were also installed as five tarballs in the real Backstage host described below. AWS transport was simulated with an SNS envelope injected into the real Events service; no live AWS account, SQS queue, SNS topic, CloudWatch alarm, or GitHub App was configured.

- AWS notifications: SNS envelope and CloudWatch field validation, exact `TopicArn` allowlisting, region recovery from the alarm ARN, notification severity mapping, save-before-detail-before-evaluate ordering on a shared scope, the native payload carrying no machine-readable metadata, the alert surviving a failed detail write, a provider failure stored as detail state, capacity release after a failed save and after a provider failure, a full ten-message batch evaluated without overflow, and no provider call when demo mode is on. One test reproduces the configuration defect behind the documented topic name: with the real `ConfigReader`, reading topic keys the way the AWS SQS module does (`topics.keys().map(topic => topics.getConfig(topic))`) throws for a dotted key such as `aws.cloudwatch` and succeeds for `aws-cloudwatch`.
- AWS alert detail table: the packaged migration is exercised against a real in-memory SQLite database through Knex, covering table and index creation, a repeated migration, rollback, skipping migrations when the host disables them, upsert by notification scope, unknown scopes, and a corrupt row that does not hide its neighbours. Retention tests cover expired reads with no intervening writes, the exact 30-day boundary, 500-row cleanup batches, preservation of refreshed rows, and cleanup recovery after a database failure. A packaging test resolves the migration directory the way the backend does and asserts that `migrations` is in `files` and that the `./package.json` subpath export needed for that resolution is present.
- AWS alert read endpoint: the tests model the **real** Notifications response, which contains no `metadata`. They cover enrichment of the current user's own rows, the plugin token being requested on behalf of that user for `targetPluginId: 'notifications'`, the fixed topic and page bounds replacing anything the caller sends, rows from another origin or topic being neither returned nor used for a table lookup, another user's stored details being unreachable, 401/403 without a user principal (with no Notifications call at all), 400 for an out-of-range or non-numeric page, alerts still returned when their details are missing or when the detail store itself fails, and 502 for a failing or unreadable Notifications backend.
- Tech Insights: separate fetch/evaluation/evidence states, annotation opt-in, private-source blocking, document size caps, deadline propagation and stalled-stream destruction, bounded concurrency, and not-evaluated facts with no document read and no provider call in demo mode.
- AWS alert inbox: parsing of the standard Notifications `created`/`updated` fields, alerts retained when a timestamp is missing or unparseable, alerts retained when the stored result breaks the evaluation contract, alerts retained with an honest "details unavailable" message and no re-check action when the stored details are missing or unreadable, the recorded time of the automatic assessment shown separately from the notification timestamps, and manual re-checks kept attached to the alert that produced them and discarded when the list reloads. A frontend test asserts that the inbox calls `/api/jev-operations-support/aws-alerts` rather than the Notifications list, and that a 404 from it is reported as a setup hint.

Receive-time AWS summarization uses the root `confidenceThreshold`; a test asserts that the same provider answers yield different finding statuses under different configured thresholds, matching the manual endpoint's behavior.

## Real Backstage host

Version 0.2.0 was installed as packed artifacts in a separate **Backstage 1.55.0** host generated with `@backstage/create-app@0.9.2`, using Node.js 22.23.2 and Yarn 4.13.0. The host used the new frontend system, the normal auth/catalog/permission backend plugins, a development guest identity, an allow-all permission policy, and an in-memory SQLite database. Only official synthetic example catalog entries were loaded.

All six workflows were exercised through the actual Backstage browser UI and called the live `jev-1.13.0` API. Template, ownership, and search candidates came from the real Catalog API. A result link opened the corresponding catalog entity, whose Operations Support tab correctly seeded the entity context. An unauthenticated HTTP evaluation request returned **401**. See [the recorded host checks](backstage-host-smoke.json).

This verifies a local integration, not a production identity provider, an organization's permission policy, or model accuracy. Host-specific production validation remains the installer's responsibility. The legacy frontend adapter is covered by component/type checks; this end-to-end run used the new frontend system.

The older recorded host run covers the six workflows at version 0.2.0. A separate [0.3.0 integration report](integration-host-0.3.0.json) records the new verification on 2026-09-19, using TechDocs backend 2.3.0, Notifications backend 0.6.9, Tech Insights backend 3.1.0 and its JSON rules module 0.10.0. The frontend was built with Webpack and served locally; the backend ran on Node.js 22.

- A Japanese synthetic TechDocs page loaded into an initially empty entity editor through authenticated HTTP. The real TechDocs backend serves generated HTML as `text/plain`; the loader accepted it, removed page chrome, and waited for an explicit Evaluate action. Live Jev then returned four supported readiness checks (0.97, 0.97, 0.96 and 0.98).
- The actual Tech Insights scheduler fetched this project's public README, called live Jev, stored four findings as facts, and ran the native JSON rules check. This was a connectivity and storage check, not a claim that the README is a complete service runbook.
- A synthetic Japanese CloudWatch alarm passed through the real Events and Notifications services and the plugin's migrated SQLite detail table. The user-scoped inbox displayed the persisted live assessment (`impact: unknown`, `area: capacity`). A browser re-check returned a separate result without changing the stored automatic result or the AWS `ALARM` state.
- Unauthenticated evaluation, native Notifications, and enriched alert reads returned 401. A bad GitHub webhook signature returned 401, while a valid signature for an unlisted repository reached the handler and was ignored. The GitHub client also read the real directory pull request's file list and pinned contents. A locally signed delivery for [this change's pull request](https://github.com/namayasai/backstage-jev-operations-support/pull/1) fetched its pinned README through the real GitHub API and evaluated it with live Jev in 2,842 ms; replaying the same delivery returned `duplicate` in 4 ms. No GitHub webhook registration was created.
- All five tarballs included license text; the AWS archive included its migration. Backstage discovered the backend configuration schema by package name, with the API key and both webhook credentials marked secret. A credential scan found no matches in the tracked/untracked source or packed archives.

These checks use guest authentication, an allow-all test permission policy, synthetic alerts, a public document source, and an in-memory database. They do not establish production AWS delivery, cross-instance reliability, a production identity policy, or model accuracy. The standard SQS/Events delivery limitations documented in the AWS guide still apply.

Backstage integration adapters also have automated tests for catalog filtering, explicit full-text fields and stable ordering, the host fetch API, readable non-JSON and Backstage error responses, TechDocs HTML extraction/path validation, catalog links, and clearing state on entity navigation. The entity TechDocs loader uses the host fetch API and waits for an explicit evaluation action; a missing TechDocs backend does not prevent the workbench from loading.

The Backstage 1.55.0 catalog backend was also checked directly: omitting full-text fields returned zero results for `example-website`, while explicitly passing `metadata.name`, `metadata.title`, `metadata.description`, and `metadata.tags` returned the expected entity. The adapter therefore keeps these metadata paths explicit; the installed CatalogClient forwards them without remapping.

Independent review found two defects before release: entity state survived navigation, and contradictory provider decisions were accepted. Both were corrected and regression tested.

The three 0.2.0 packed artifacts were also installed into a separate temporary npm consumer with a local shared-package override. This checks package resolution independently of the development workspaces.
