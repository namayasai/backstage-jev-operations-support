# Changelog

## Unreleased

- Move manual incident reports into a dedicated Triage sidebar page. Add optional OpenAI, Claude, and OpenAI-compatible response suggestions after successful Jev incident assessment, including stored ALARM results. Keep Jev results available if suggestion generation fails. Name pre-check workflows by the task being checked.

- Position the manual workflow page as Pre-check: explain when to use each workflow before a PR, handover or service creation, name inputs by their purpose, and label the action and results as a pre-check.

- Add a dedicated Alerts sidebar page with Type, notification Severity, Log and Jev quick-check columns. Open details on row selection, keep Refresh visible, and use workflow tabs in the separate Playground page.

- Preserve the 300-file readiness limit when change review uses smaller listing pages. Report excess matching documents after pending, retain unfinished status obligations across superseded retries, and resolve old pending statuses on their original commit when a PR moves.

Two additions, one on each side of the Tech Insights module, both read-only or opt-in:

- Added a second, opt-in Tech Insights fact retriever, `jevOwnerSuggestionFactRetriever` (`jevOperationsSupport.techInsights.ownerSuggestion`, off by default), that suggests a responsible catalog Group for entities that appear to have no real owner: `spec.owner` missing, empty, or matching a configured "unowned" value (`unknown`, `guests`, `group:default/guests` by default, compared case-insensitively as written and as a normalised ref, via the new shared `isUnownedOwner`/`defaultUnownedOwnerValues` in the common package), or naming a Group that does not exist in the catalog. Selection is bound-after, not bound-before: every run first *scans* up to `maxScannedEntities` (default 2000) catalog entities of the configured `kinds` for ownerless ones — `maxEntities` no longer caps the initial catalog page, which previously meant an ownerless entity sorting after the first `maxEntities` catalog entities was never reached at all — then selects at most `maxEntities` of the found candidates, rotating which slice by calendar day when there are more candidates than that, so a large ownerless population is covered a window at a time across consecutive runs instead of stalling on the same entities forever. Only the selected window gets the two remaining catalog reads: one batched Group-existence lookup for its dangling-Group candidates (never one call per entity, and never for the full scan), and one batched re-fetch of its own full entity records. If the Group-existence lookup fails, the affected window entities get **no fact row at all** (not a guessed `catalog-unavailable` row) — an owner that merely *parses* as a Group ref may still be a real, existing owner. An entity with a real, existing owner — Group or User — also gets no fact row at all. The request sent to Jev carries only the entity's own name, title, description, tags, kind, type, lifecycle, and system, plus up to `maxGroups` catalog Group candidates (title/description/tags, the same mapping the AWS notifications module's owner suggestion uses) — never documentation content, and it never reads or writes `spec.owner`. Costs at most `maxEntities` Jev calls per scheduled run. Facts now separate *why the entity was selected* (`selection`: `unowned` / `owner-not-found`, always present) from *why evaluation did not produce a suggestion* (`reason`, a closed failure/not-evaluated code, empty when evaluated), and add `checkedOwner` (the raw `spec.owner` value the row was actually computed for), so a consumer can tell a still-current row from a stale one. `TechInsightFact.entity` (for both this retriever and the existing readiness one) is now stored fully lower-cased, matching `stringifyEntityRef`'s own canonicalisation, since `@backstage-community/plugin-tech-insights-backend` is not installed in this repo and its internal handling of that field's casing could not be verified from source. See [docs/tech-insights.md](docs/tech-insights.md). The closed sets this stores now live in the common package as `jevOwnerSuggestionSelections` and `jevOwnerSuggestionReasons`, alongside `awsAlertOwnerErrorCodes`. A malformed setting inside an otherwise-*disabled* `ownerSuggestion` block no longer prevents the always-on readiness retriever from registering (`buildJevTechInsightsFactRetrievers` now validates `enabled` on its own first).
- Added two read-only entity page cards to the frontend package, `EntityJevReadinessCard` and `EntityJevOwnerSuggestionCard` (`plugins/jev-operations-support/src/entityCards.tsx`), exported from both the legacy plugin (`createComponentExtension`) and `/alpha` (`EntityCardBlueprint`, with an object-predicate `filter` — the string-expression form is deprecated in the installed `@backstage/plugin-catalog-react`). They show the *latest scheduled* result from the two Tech Insights fact retrievers above, read directly from the Tech Insights backend's `GET /facts/latest` route via `discoveryApiRef`/`fetchApiRef`, building the exact same query `TechInsightsClient.getFacts` does (`entity=<ref>&ids[0]=<retrieverId>`, verified against its source in `node_modules`) — no dependency on the Tech Insights frontend plugin, and no Live switch or "Check now": nothing on either card ever triggers an evaluation, and each fetch is aborted on unmount or when the viewed entity changes. The readiness card renders exactly the aggregate evidence status and counts the retriever stores (it has no per-check breakdown to show) and keeps its loading skeleton; the owner card renders nothing while loading (no shell flash on the common case of an already-owned entity) and renders only when a fact row exists **and matches the entity's current `spec.owner`** — it never trusts the stored row's own `selection`/`reason` on faith, always re-deriving "no owner is set" from the live entity with the same shared `isUnownedOwner` rule the retriever uses (an `unownedValues` prop is available to match a customised backend setting), and otherwise (a row computed for an owner value the entity no longer has) renders nothing, since the row is stale. For the one remaining case that would otherwise assert an un-verified catalog fact — an unchanged `owner-not-found` row — the card now additionally confirms live, via `catalogApiRef.getEntityByRef`, that the Group still does not exist before saying so (rendering nothing while that check is in flight, on failure, or if the Group has since been created); this is not cached in the stored fact, since the fact is a scheduled snapshot that can go stale between runs. It links the suggested Group and states plainly that it is a suggestion that does not change the entity's owner. Both handle a missing Tech Insights backend (a quiet line, not an error), no result yet, a stale (>7 day) result, and a fetch error, and treat an unknown or malformed fact payload as "no facts" rather than crashing. See [docs/installation.md](docs/installation.md), which also now documents the cards' full extension ids and that every Tech Insights fact is readable under the Tech Insights `read` permission regardless of catalog entity permissions. On the new frontend system, a custom `unownedValues` currently requires overriding the `owner-suggestion` `EntityCardBlueprint` extension yourself (see installation.md) — the installed `@backstage/frontend-plugin-api`'s `configSchema` mechanism requires Zod v4, and this repository is on Zod v3, so wiring app-config-driven `unownedValues` through the blueprint itself was not attempted here rather than mixing Zod major versions in one package.
- Follow-up hardening after review: rotation now advances a full `maxEntities`-sized step per UTC day instead of one candidate at a time — the earlier version needed `candidates.length` days to cover a large ownerless population (500 candidates ÷ a window of 20 would have taken 481 days, each candidate billed 20 Jev calls along the way); it now covers everyone within `ceil(candidates.length / maxEntities)` days, each evaluated close to once per cycle. The owner-suggestion catalog scan now uses `CatalogClient.queryEntities` cursor pagination instead of offset paging (stable under concurrent catalog writes), and the whole run now reuses one `CatalogClient` and one auth token across the scan, the dangling-Group check, the window's entity re-fetch, and the Group candidate pool, instead of requesting a fresh token for each. A scan cut off by `maxScannedEntities` now logs a count-only warning (`scanned`, `maxScannedEntities`). `ownerSuggestion.*` config validation errors now name the full config path (e.g. `jevOperationsSupport.techInsights.ownerSuggestion.maxScannedEntities`), not just the bare key. **Upgrade note: readiness facts written by 0.3.0 were keyed with the entity's original casing; after this release they are keyed canonically (lower-cased), which is what every Tech Insights read path already sends. Facts written before the upgrade are not read back — the next scheduled run repopulates them.**

The frontend UI was rebuilt on Backstage `core-components` and Material UI, replacing the previous hand-rolled markup. The page is now two views, **Alerts** and **Playground**; incident triage moved into the alert inbox itself (a "Triage a report" pane next to the alert list) rather than being a separate workflow tab.

Automatic checks are opt-in: **Live defaults to off**, and nothing is sent to the provider until the reader either chooses "Check now" (or "Rank now" in search) or turns Live on, a choice remembered per browser (`localStorage`). Once a reader turns Live on, an entity tab checks readiness automatically as its TechDocs loads (TechDocs itself still loads into the editor either way), and an alert the reader opens is assessed automatically if it has no stored result. A host can still force automatic sends off for a given usage regardless of the reader's preference with `live={false}` (`JevWorkbench`, `AlertInbox`, `JevRerankedResults`, `JevTemplateAdvisor`). `AlertInbox` now polls every 30 seconds by default; pass `pollMs={0}` to disable it.

- The stored Live preference is now backed by a single module-level store shared by every mounted view (`useSyncExternalStore`, with a `storage`-event listener for other tabs), so it is a single gate for every automatic send: toggling it in one view updates every other mounted view at once, the alert inbox's report triage pane honours it (with its own Live switch and Check now button) instead of always sending, and a view the reader is not looking at (a hidden tab, a closed report pane) sends and polls nothing.
- Auto-assessment of an alert now expresses the reader's click-time intent only: it fires for an alert explicitly clicked while Live, the report pane, and the current view all allow it at that instant, never for the row selected automatically on load or after a background refresh, and never more than once per alert per page load. If any of those conditions later turns blocking, the pending intent is dropped rather than firing once it lifts again.
- A background refresh of the alert list no longer moves the reader to a different alert; if the selected alert falls off the page, it stays on screen with a note that it is no longer on the current page. If nothing was selected (most likely because the first load failed), a background refresh that succeeds now seeds the selection instead of leaving the reader with an empty details pane.
- `evaluate` callbacks may now receive a second argument, `{ signal }`, an `AbortSignal` for the in-flight request. A superseded automatic check aborts the one still in flight, as does an automatic check when the hook becomes paused or Live turns off (not on a plain workflow switch, whose request key already changed). A manual re-check or owner suggestion in the alert inbox is aborted on unmount and when a reload or paging invalidates the list it belongs to. Every abort is silent: it is never reported as a failure. After a failed check, automatic retries back off (honouring a `Retry-After` response header, otherwise an exponential delay) instead of retrying immediately; `useLiveEvaluation` now exposes this as `retryAt`, and the workbench and report triage panes show "Retrying automatically after a failure" instead of implying the reader is the one being waited on.
- New runtime dependencies: `@backstage/core-components`, `@material-ui/core`, `@material-ui/lab`.
- Removed the `@material-ui/icons` dependency: its deep-path modules (`@material-ui/icons/ExpandMore`, `@material-ui/icons/Close`) are CommonJS, and a default import of one from this package's published ESM (`dist/*.mjs`) resolves to the whole CJS module object rather than the component under a real webpack/Rspack host's strict ESM interop, crashing every view that renders a finding ("Element type is invalid ... Check the render method of `FindingRow`."). The two icons used (expand/collapse chevron, close) are now small `SvgIcon`-based components in `./icons`.
- The legacy `JevPage` routable extension now renders its own page header (title and subtitle), matching the new frontend system's page.
- Finding rows are now an accessible disclosure (a labelled expand/collapse button) instead of a Material UI Accordion, so the summary text is no longer swallowed by the expand control.
- Finding row detail ids are now generated with React's `useId`, so two result panes rendering the same finding ids at once (e.g. a manual re-check next to the stored result) no longer produce duplicate DOM ids or ambiguous `aria-controls`.
- The two stored-result explanatory notes in the alert detail pane are plain, static prose; they no longer carry `role="status"`, which is for text that changes on its own.
- The "Every alert on this page has recovered." message now renders outside the alert `<List>` instead of as a stray `<div>` inside it.
- Polling now stops (clearing its interval) rather than ticking as a no-op once the optional AWS module has proven unavailable, and resumes automatically after a later explicit load succeeds.
- Added two new frontend subpath exports that put a workflow where it is chosen, instead of only on the Playground page: `./search` (`JevRerankedResults`, reorders a Backstage search page's results using the `search` workflow, in place of `<SearchResult>`) and `./scaffolder` (`JevTemplateAdvisor`, a standalone "Which template fits?" card using the `templates` workflow). `@backstage/plugin-search-react` is now an optional peer dependency, required only by `./search`; the main `.`/`./alpha` exports do not import it, so a host that does not use `./search` is unaffected. Both new components share the same Live preference and `/evaluate` call as the rest of the plugin.
- **Disclosure:** with `JevRerankedResults` installed, choosing "Rank now" or turning Live on (off by default, opt-in per reader) sends the query, and the indexed title and an excerpt of the body text of the top results, to TypeSafe through the Backstage backend. Search indexes commonly include content from private documentation the reader may not otherwise be able to read directly. A host can force this off for a given usage with the new `live={false}` prop (also added to `JevWorkbench`, `AlertInbox`, and `JevTemplateAdvisor`), or leave it to each reader's own Live switch; the `jev-operations-support.evaluate` permission and the backend's evaluation rate limit still apply to these calls like any other.
- `JevRerankedResults` now fits its shortlist to the shared 24,000-byte evaluation budget instead of silently never reranking realistic result sets (20 results at up to 1,500 characters of description each is roughly 31 KB unshortened, over budget on its own). Titles and descriptions are capped in UTF-16 code units (200 / 1,500, matching the schema) by cutting on code-point boundaries, so a surrogate pair is never split. When the natural shortlist does not fit, descriptions are shortened first, via a bounded binary search over an even per-candidate byte allowance against the real (JSON-escaped) request size — not a fixed per-attempt decrement, which could collapse excerpts to almost nothing after a single overshoot on escape-heavy text (control characters, quotes, backslashes). Only if even title-only candidates do not fit are candidates dropped from the tail; and if even a single title-only candidate does not fit alongside the query itself, the shortlist is empty and the query is reported as too long to rank against, rather than sending one candidate over budget. The caption says so briefly when a shortened shortlist was the one actually used to reorder. Candidate ids (previously a bare 200-character prefix of the location) are now made unique deterministically when two results would otherwise collide or need truncating, so neither result silently loses its own score.
- `JevRerankedResults` now has an honest caption and a visible Live switch in every state it renders one — waiting for the quiet period, Live off (with a "Rank now" button), a request that could not be built, a failed check, a low-confidence result — instead of only while a reorder is actually applied; it applies scores only when they were computed for exactly the current question and exactly the current shortlist (previously a fragile positional id comparison), looked up by index into the current engine-order head rather than through a `Map` keyed on the result object's identity (which a host re-render handing back fresh-but-content-equal result objects made silently dead, since the shortlist itself is cached by content, not by that array's identity). The caption claims a reorder only when at least one result actually received a score in that render; if scores land but none can be matched to the current head, the caption falls back to the same "asking Jev" / "unranked" wording as before any scores arrived. With zero results — including an untouched search box — no caption or Live switch is shown at all, the same as while the search itself is loading; previously the reader saw schema-internal wording ("This workflow needs at least one candidate.").
- `useLivePreference()` no longer takes an initial-value argument: the module default is `false` (Live is opt-in), and a stored preference always wins, so a host passing `live={false}` to force a specific view off can no longer be silently overridden by another mounted view supplying its own initial value. `useSyncExternalStore` also now supplies a `getServerSnapshot`.
- `JevTemplateAdvisor` now says plainly ("Jev suggested *title*, but its catalog reference could not be resolved.") when Jev recommends a candidate whose `entityRef` cannot be parsed, instead of rendering nothing.
- When a host forces automatic sends off with `live={false}` (`JevWorkbench`, `AlertInbox`'s report triage pane, `JevTemplateAdvisor`, `JevRerankedResults`), the explanation ("Automatic checks are turned off for this view.") is now visible caption text next to the switch, linked to it with `aria-describedby`, instead of living only in a `title` attribute unreachable by keyboard or screen reader. Extracted the shared `LiveSwitch` component.
- Extracted the shared `/evaluate` call into a new `useJevEvaluate` hook and the catalog-to-candidate mapping into `catalogCandidates.ts`, both reused by the existing page, the new search component, and the new scaffolder component. `responseError` moved with the evaluate call but is still re-exported from `BackstagePage.tsx` for existing imports.
- The evaluation-contract guard (`isEvaluationResult`) now checks every finding's `kind` (`noul`/`choice`/`score`), that `value` is a finite number for `noul`/`score` or a string for `choice`, and that `guidance` is a string, not just `id`/`title`/`statement`/`status`. A malformed or wrong-workflow result — from a bad provider response or a future schema mismatch — is reported as an ordinary error instead of being rendered (which previously risked "undefined" text or a `search` reorder sorted on `NaN`); this applies everywhere a result is received: the workbench, search reranking, the template advisor, report triage, and alert re-checks.
- `JevRerankedResults` now says "Jev's scores could not be matched to these results." when scores land for the current question and shortlist but none can be matched to the current results, distinct from the "Asking Jev to rank these results…" caption shown while a check is still in flight.
- `JevRerankedResults`'s "shortened excerpts" note and its low-confidence note are no longer mutually exclusive: when both apply, the caption now reads "Reordered by Jev — low confidence for some results; shortened excerpts were used". A new caption also reports when fewer of the head results were scored than are in the head ("Reordered by Jev — N of M results ranked"), folded into the same combinable list.
- `JevRerankedResults`'s shortlist memoization key now folds in a cheap FNV-1a hash of each result's body (the same collapsed-and-capped 1,500-unit sample `fitShortlist` would send), not just its length, so a reindexed body of equal length no longer reuses a stale excerpt.
- Added an optional `jevOperationsSupport.awsNotifications.ownerSuggestion` setting (off by default) that makes a second Jev call at alarm receipt, alongside incident triage, suggesting an owning catalog Group from the same alarm context. It runs only for an active (`ALARM`) alarm whose incident evaluation succeeded, and shares the alarm's own per-process Jev capacity slot rather than claiming a second one (incident and owner evaluation for one alarm are one logical unit of work). The incident result is published in its own write as soon as it is ready, before the (potentially slower) catalog read and owner call start, so a reader never waits on the owner path to see triage that already finished; the owner path can add up to a further 2 × `timeoutMs` after that before the alert's final state appears. Its catalog `Group` read is cached in memory (single-flighted; a failure is negative-cached for the larger of a fixed 15 seconds and 2 × `timeoutMs`, separate from the much longer success cache, so a catalog outage cannot cause a pile-up of concurrent reads — though each alarm that starts a fresh read during the outage still holds its own capacity slot for up to `timeoutMs` while that read hangs). A candidate shortlist that would not fit the shared evaluation budget is shortened, and, only as a last resort, trimmed from the tail — with the allowance search re-run afterward so a kept candidate regains as much of its description as the smaller list leaves room for, rather than staying at the empty string the drop step used to decide how many to keep; `alert-context-too-large` is reserved for the alarm context alone being too large, with a new `invalid-owner-request` code for any other schema refusal. The result is stored as `ownerStatus`/`ownerResult`/`ownerCandidates` (the sent shortlist's entity refs and titles, up to 20 per alarm, in the same table and retention as the rest of the row)/`ownerShortened`/`ownerErrorCode` on the existing detail row; all of these are omitted entirely when the feature is disabled or the alarm is not `ALARM`, so old rows, disabled installs, and non-`ALARM` alerts are indistinguishable. Every write of a redelivered SNS message's detail row — not only its final one — now preserves an earlier delivery's already-`evaluated` owner suggestion instead of overwriting it with a transient failure, including when the redelivery never reaches a second write at all (capacity exhausted, no evaluator configured) or its own final write throws; a preserved suggestion can end up next to a later, failed incident result, and its own `evaluatedAt` still reflects when it was actually made. Two concurrent deliveries of the same scope remain last-writer-wins, as for any other column of the row.
- Moved the catalog-entity-to-candidate mapping and a shared `truncateCodePoints`/`fitCandidatesToBudget` into the common package (`entityToCandidate`, `catalogCandidateOrderFields`, `truncateCodePoints`, `fitCandidatesToBudget`), also moving the AWS module's `awsAlertOwnerErrorCodes`/`AwsAlertOwnerErrorCode` there (re-exported from the AWS module for compatibility) so the frontend's catalog picker, error-code coverage test, and the AWS module's owner suggestion all share one source of truth without a frontend test needing to import a backend module's source.
- The AWS alert inbox shows a stored owner suggestion in the alert list (an "Owner: <title>" chip, only for a confident match) and in the detail pane ("Suggested owner from receipt", including a note when descriptions were shortened to fit), and the existing manual "Suggest owning team" action now relabels to "Re-suggest owning team" once a stored suggestion exists. A runner-up candidate in a result's probability breakdown is now labelled from the stored shortlist when available, or "Candidate N" instead of a raw internal key when it is not.
- The GitHub pull request webhook can now report its already-computed readiness result back to GitHub instead of leaving it only in the HTTP response, via the new `jevOperationsSupport.githubWebhook.report` config key (`none` | `status` | `status+comment`, defaulting to `none` — every existing guarantee holds unchanged in that default; `report`/`blockOn`/`queueLength` are validated at startup even when the webhook is otherwise unconfigured, and `report` other than `none` without a secret and token is itself a startup error). This never widens what is read from GitHub or sent to Jev: the same changed Markdown documents, under the same allowlists and limits, are evaluated exactly as before; only where the result is reported changes. `status` writes a `jev/readiness` commit status on the pull request's head SHA. **Invariant: every `pending` this writes gets exactly one final state (`success`/`failure` from a real result, `error`, or a neutral `success` when the pull request changed mid-check), and nothing at all is written for a delivery that never confirmed a matching document** — a GitHub read failure before a match is confirmed (e.g. the changed-file listing hitting its own limit) writes nothing and forgets the delivery so redelivery can retry, while a limit violation discovered *after* a match is confirmed (too many matching documents) resolves the `pending` with `error`, same as a Jev failure or the deadline. `pending`/`error` are ordinary statuses that a required branch-protection check still treats as blocking regardless of `blockOn` — the docs now say plainly not to mark `jev/readiness` required unless that's intended. `status+comment` also creates or updates a single hidden-marker PR comment (found via the token's user's *newest* comments first — the issue-comments endpoint has no sort/direction parameters of its own, so this reads backwards from the last page using its `Link: rel="last"` header, within the existing 3-page/300-comment bound) with a per-document table; every changed-file path is rendered as a size-correct, pipe-safe, control-character-stripped inline code span so a hostile path (a Markdown link, an `<img>` tag, `@mentions`, pipes, embedded backticks) can never become active Markdown/HTML, the check title/guidance/model are escaped the same way as defense in depth, and the whole body is capped at 60,000 characters with an explicit truncation row. `blockOn: attention` (default `never`) fails the status on an `attention` finding; a low-confidence `review` finding never blocks by itself. Reporting requires a token with **Commit statuses: write** (`status`) or also **Issues: write** plus **Pull requests: read** (`status+comment` — the PR comment endpoints are part of the Issues API) in addition to the existing read scopes — GitHub Check Runs cannot be written with a personal access token (GitHub Apps only), which is why this uses commit statuses instead. With reporting on, the webhook checks a payload-obvious fork refusal before ever queueing (so a refused fork never occupies a queue slot), then responds `202 Accepted` immediately and evaluates in a bounded, single-worker, in-process background queue (default length 20, also bounded by the existing delivery-dedupe capacity, no persistence — a restart loses queued work and can leave a dangling `pending`; recover by pushing a new commit or redelivering after the dedupe TTL); a newer delivery for the same pull request supersedes an older one still waiting in that queue. A delivery is remembered (for dedupe) only once its final write actually succeeds; if the write itself fails, the delivery id is forgotten so redelivery retries it. The per-delivery deadline becomes configurable up to 60 s in this mode (still 1000–8000 ms with `report: none`, which continues to process synchronously exactly as before). The pull request's head/base is re-checked during evaluation and again immediately before the final write; only a *confirmed* moved head suppresses the real result (an unconfirmed recheck failure still writes the real result, since it is no riskier than the `pending` already posted). The authenticated `/status` route now also reports non-secret queue facts (report mode, queue length, last delivery outcome code/time) when the webhook is configured. `formatFindingValue` and the finding status labels moved to `@namayasai/backstage-plugin-jev-operations-support-common` (`formatFindingValue`, `findingStatusLabels`, `negativeFindingDisclaimer`) so the workbench UI and the new report comment describe a finding identically; `plugins/jev-operations-support/src/Findings.tsx` and `Workbench.tsx` now use them instead of their own copies.
- The GitHub pull request webhook can now also run an opt-in **change review** of the pull request diff itself, alongside readiness, via the new `jevOperationsSupport.githubWebhook.changeReview` block (`enabled: false` by default; requires an explicit `paths` allowlist when enabled, plus `maxFiles`/`maxPatchBytes` budgets — see `docs/github-webhook.md`). It assembles a bounded summary — title, description, changed-file list, and diff excerpts for allow-listed, non-sensitive paths only, per the pure `changeReview.ts` core's own extensively documented rules — and runs the existing `change-risk` workflow against it once per accepted delivery (never a second GitHub endpoint; reuses the same pull-request-files listing and pull request metadata readiness already reads). Requires `report: status` or `status+comment` — `changeReview.enabled: true` with `report: none` is a startup error, since the result would otherwise never be visible anywhere. Reports under a second, independent commit status context, `jev/change-review` (own pending→final invariant, own `blockOn: attention` semantics derived honestly from the four `change-risk` checks — a low probability on a compatibility/migration/access concern is "not established," never a safety pass), and — in `status+comment` mode — a new "Change review" section in the same shared marker comment as readiness's own table, with a collapsed disclosure of what was included, listed only, excluded as sensitive, or withheld as an unsupported path, rendered through the same inert code-span/Markdown-escaping readiness's comment already uses. A change-review failure never affects the readiness result or vice versa; readiness's own behaviour is completely unchanged when `changeReview` is left unset. `docs/change-review-design.md`, the design note for the pure core, is now a pointer to the real docs (`docs/github-webhook.md`'s "Change review" section) and to `changeReview.ts`'s own module doc comment.
- Follow-up hardening for the change-review feature above (security review): readiness and change review now share a SINGLE pull-request read and a single changed-file listing read per delivery instead of each reading GitHub independently (the listing's own tolerant paginator also now handles a single page exceeding GitHub's 1 MiB response cap — truncating past page 1, erroring on page 1 itself since nothing was collected yet — and keeps no `patch`/`additions`/`deletions`/`previous_filename` at all, not merely unused ones, when change review is disabled); `jev/change-review` error statuses now use their own wording throughout (e.g. "Change review exceeded its processing deadline.", never readiness's "Jev readiness check exceeded its processing deadline."); readiness evaluation uses a shortened sub-deadline to leave time for change review (shared reads and final reporting can still consume this reserve); a delivery where only one of the two contexts finished is now remembered as `partial` and a redelivery of the same id resumes only the unfinished context (no duplicate provider call or status write for the one that already finished); and the combined PR comment now reserves the change-review section's own budget FIRST (degrading its own disclosure-list entry caps if it alone would not fit) before giving readiness's table the remainder, so a large readiness table can no longer silently truncate the change-review section's disclaimers or disclosure block off the end of the 60,000-character comment.
- Follow-up hardening for the GitHub webhook reporting feature above: every status description now names the originating pull request (e.g. `PR #12 · 2 clear · 1 attention — advisory`), since a commit status is keyed only by (repository, SHA, context) and two open PRs sharing a commit would otherwise overwrite each other's status with no indication of whose it was — docs now call this out prominently next to the `blockOn: attention` guidance. The final status write now retries a transient failure (a network error, a `5xx`, or GitHub's `403`/`429` rate limiting — never `401`/`404`/`422`) up to twice more with backoff, in its own 10-second budget, with the pre-write head recheck given its own separate 3-second budget so it cannot starve that retry budget, and the comment kept in a further separate 5-second best-effort budget; docs now state plainly that reporting mode always answers the webhook itself with `202`, so GitHub never automatically redelivers a failed report — recovery is a new commit or a manual Redeliver. The report comment is now skipped entirely when the commit status write itself failed (a result table next to a stuck `pending` would mislead), and its hidden marker is now matched only at the very start of a comment body rather than anywhere inside it. The Markdown sanitiser now also strips Unicode bidi-override, zero-width, and other hidden/format characters (a right-to-left override could otherwise visually disguise a path without changing its bytes) from both paths and the provider's model string, written throughout as numeric code points rather than escape sequences or literal characters so the exact set stripped is auditable from a diff. The (bogus, since the per-issue-comments endpoint ignores them) `sort`/`direction` query parameters used to search for the report comment are replaced with the endpoint's actual `Link: rel="last"` header, read backwards from the last page. The shared delivery-dedupe capacity guard is now also enforced in reporting mode, and the payload-obvious fork check runs before a delivery ever occupies a queue slot.

- Added an AWS alert inbox to the frontend, with a local manual re-check that is not written back to the notification.

Recipients, inbox identity, titles, alarm reasons, and read/saved state stay with standard Notifications; detail rows are cleaned up after 30 days during ordinary writes, and an alert without them stays visible.
